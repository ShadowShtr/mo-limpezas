## 3. Incidente de marcar pagamento como pago — estado consolidado

O PR #62 documentou duas causas independentes:

1. o CHECK de `cash_flow_entries` não aceitava `fixed_variable_payment`;
2. a UI descartava o `{ ok: false, error }` retornado pela action.

A migration 075 corrigiu o CHECK e o código passou a tratar o retorno da action.

A arquitetura autoritativa para frente é:

```text
UI
→ Server Action
→ mark_payment_paid()
→ atualização do pagamento + saída de caixa na mesma transação
→ cash_entry_id
→ read/snapshot autoritativo
```

A identidade de origem do movimento é:

```text
reference_type = 'fixed_variable_payment'
reference_id   = payment.id
```

E deve continuar protegida por unicidade de origem por empresa.

### Regras que não podem voltar a regredir

- não fazer `UPDATE status='pago'` direto pela UI;
- não fazer `INSERT cash_flow_entries` manual para "completar" uma marcação;
- não engolir `{ ok: false }`;
- retry/double click não podem criar dois movimentos;
- `unmark_payment_paid()` remove apenas o movimento origin-linked;
- um movimento manual gémeo por valor/data deve sobreviver.

## 6. Nova decisão de produto — Pagamentos será a fonte operacional única

Foi recebido feedback de que:

```text
Financeiro → Contas → Despesas pendentes
```

e

```text
Financeiro → Pagamentos
```

representam praticamente o mesmo conceito em locais separados.

Sintoma relatado:

```text
Contas → Despesas pendentes → Marcar como pago
→ item desaparece
→ não fica claro para onde foi
```

Decisão planeada:

```text
PAGAMENTOS = única área operacional de contas a pagar
```

Contas deixa de ter uma segunda lista mutável com um segundo botão de marcar como pago.

Fluxo alvo:

```text
OBRIGAÇÃO
→ PAGAMENTO
→ MOVIMENTO DE CAIXA
→ CONCILIAÇÃO
```

Uma obrigação deve ter:

```text
1 identidade
1 estado
1 caminho de pagamento
no máximo 1 movimento origin-linked
1 histórico auditável
```

Plano detalhado:

```text
docs/FINANCEIRO-PAGAMENTOS-FONTE-UNICA-PLANO.md
```

## 8. Blindagem financeira obrigatória da próxima frente

A futura implementação precisa fechar, com testes/guards, estas classes:

### Identidade / duplicação

```text
VISIBLE_MARK_PAID_IMPLEMENTATIONS = 1
PAYMENT_STATUS_DIRECT_WRITE_OUTSIDE_CANONICAL = 0
FIXED_PAYMENT_CASHFLOW_DIRECT_INSERT = 0
PAID_PAYMENT_DOUBLE_COUNT = 0
```

### Render nunca escreve

```text
AUTO_WRITE_ON_RENDER = 0
```

Abrir página, refresh, mudar mês ou mostrar reminder:

```text
0 INSERT
0 UPDATE
0 DELETE
```

`ensureMonth` e `shiftDate` continuam em quarentena.

### Erro não vira zero

```text
FINANCIAL_QUERY_ERROR_AS_ZERO = 0
```

Falha de query deve aparecer como `Indisponível`/erro, nunca `0,00 €` falso.

### Estado pago não é editado silenciosamente

Para campos com efeito económico:

```text
Pago
→ Reabrir
→ unmark_payment_paid()
→ editar
→ pagar novamente
```

Não permitir alterar `amount`/categoria num payment pago sem refletir o cash-flow de forma transacional.

### Delete

Pagamento pago com movimento ligado não pode ser eliminado por um botão genérico.

### Período fechado

Marcar, desmarcar ou alterar efeito económico em período fechado deve falhar fechado.

### Timeout depois de COMMIT

Se o cliente perder a resposta:

```text
não recriar movimento
→ refetch autoritativo
→ decidir pelo estado do servidor
```

### Dois utilizadores ao mesmo tempo

A e B tentam pagar a mesma obrigação:

```text
payment = pago
origin-linked cashflow count = 1
```

B recebe estado autoritativo, nunca segundo lançamento.
