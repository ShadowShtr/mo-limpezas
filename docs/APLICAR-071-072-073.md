# Aplicar 071, 072 e 073 — guião para o SQL Editor

> **Quem executa:** o dono, no SQL Editor do dashboard Supabase.
> **Projeto:** o real (`molimpezas.pt`). Não existe ambiente de teste.
> **Ensaio prévio:** `npm run rehearse:071` — 95/95 em PGlite, aplicação e
> rollback das três, a cada execução do CI.

---

## 🔴 Antes de começar: o que isto **não** faz aparecer no ecrã

Aplicar as migrations cria a estrutura. **Não liga a aplicação a ela.**

Depois de aplicar, isto passa a funcionar:

| Funciona logo | Porquê |
|---|---|
| Categorias em Contas | a UI já lê `expense_categories` |
| Botão «Criar categorias sugeridas» | a action já existe |
| Despesa com Combustível | `createCashFlowEntry` já grava `expense_category_id` |
| Donut por categoria | o agregador já prefere a categoria estruturada |

E isto **continua sem funcionar**, por decisão nossa:

| Não funciona ainda | O que falta |
|---|---|
| Pagamento pago → saída no Fluxo de Caixa | `setPaymentStatus` ainda não chama `mark_payment_paid` |
| Fatura criada pela RPC | `generateInvoices` ainda não chama `create_invoice_with_items` |

Foi assim que combinámos: primeiro aplicar e conferir a base, só depois ligar o
runtime. Testar «marcar pagamento como pago» logo a seguir a aplicar vai dar o
comportamento antigo — e isso não é uma regressão, é o passo que ainda falta.

---

## Ordem

**071 → 072 → 073**, uma de cada vez, conferindo entre elas.

A 073 depende da 071: precisa da tabela `financial_periods` e da coluna
`expense_category_id` em `fixed_variable_payments`. A 072 é independente, mas
mantém-se a ordem numérica para o ledger ficar coerente.

## Passo 1 — Aplicar a 071

Copiar **o ficheiro inteiro** `supabase/migrations/071_finance_periods_and_expense_categories.sql`
(180 linhas) e correr no SQL Editor. Já traz `BEGIN`/`COMMIT`.

### Conferir

```sql
-- 1.1 As duas tabelas existem
SELECT to_regclass('public.expense_categories'), to_regclass('public.financial_periods');

-- 1.2 🔴 ZERO SEED — a migration não semeou nada
SELECT count(*) AS categorias FROM public.expense_categories;
-- Esperado: 0.  Qualquer outro número é um problema: quer dizer que
-- catorze categorias que a gestão nunca aprovou entraram como dado
-- contabilístico permanente.

-- 1.3 As colunas novas, e nullable
SELECT table_name, column_name, is_nullable
  FROM information_schema.columns
 WHERE column_name = 'expense_category_id';
-- Esperado: cash_flow_entries e fixed_variable_payments, ambas YES.

-- 1.4 As despesas antigas continuam sem categoria — sem backfill
SELECT count(*) FILTER (WHERE expense_category_id IS NULL) AS sem_categoria,
       count(*) AS total
  FROM public.cash_flow_entries;
-- Esperado: os dois números iguais (444 e 444, à data desta escrita).

-- 1.5 RLS ligada, com as quatro políticas
SELECT tablename, policyname FROM pg_policies
 WHERE tablename IN ('expense_categories', 'financial_periods') ORDER BY 1, 2;
-- Esperado: quatro linhas (read + write para cada tabela).
```

### Reverter a 071, se preciso

```sql
BEGIN;
ALTER TABLE public.fixed_variable_payments DROP COLUMN IF EXISTS expense_category_id;
ALTER TABLE public.cash_flow_entries       DROP COLUMN IF EXISTS expense_category_id;
DROP TABLE IF EXISTS public.financial_periods;
DROP TABLE IF EXISTS public.expense_categories;
COMMIT;
```

⚠️ Isto apaga categorias e períodos criados entretanto. Enquanto ninguém tiver
usado a funcionalidade, não há nada a perder; depois disso, há.

## Passo 3 — Aplicar a 073

Copiar `supabase/migrations/073_payment_to_cashflow.sql` (210 linhas).

### Conferir

```sql
-- 3.1 As três funções
SELECT proname FROM pg_proc
 WHERE proname IN ('is_financial_period_open', 'mark_payment_paid', 'unmark_payment_paid')
 ORDER BY 1;
-- Esperado: três linhas.

-- 3.2 Um período sem linha está aberto (a ausência é que significa aberto)
SELECT public.is_financial_period_open(
  (SELECT id FROM public.companies LIMIT 1), 2026, 8) AS agosto_aberto;
-- Esperado: true.

-- 3.3 🔴 Nenhum pagamento já pago ganhou movimento de caixa —
--     a 073 não faz backfill, de propósito.
SELECT count(*) AS pagos_sem_movimento
  FROM public.fixed_variable_payments p
 WHERE p.status = 'pago'
   AND NOT EXISTS (
     SELECT 1 FROM public.cash_flow_entries c
      WHERE c.reference_type = 'fixed_variable_payment' AND c.reference_id = p.id);
-- Esperado: o número de pagamentos já pagos, inalterado.
-- Reconciliá-los é uma decisão de negócio com dados reais, não um efeito
-- colateral de uma migration.
```

> Não testar `mark_payment_paid` à mão num pagamento real: criaria uma saída de
> caixa verdadeira. Fica para a validação no ecrã, depois de ligar o runtime.

### Reverter a 073

```sql
BEGIN;
DROP FUNCTION IF EXISTS public.unmark_payment_paid(uuid, uuid);
DROP FUNCTION IF EXISTS public.mark_payment_paid(uuid, uuid, date);
DROP FUNCTION IF EXISTS public.is_financial_period_open(uuid, int, int);
COMMIT;
```

## O que está em jogo enquanto isto não acontece

Cada pagamento marcado como pago continua a **não** entrar no Fluxo de Caixa.
Os Custos do mês ficam por baixo do real e a Margem por cima — e é o número
da Margem que se usa para decidir.
