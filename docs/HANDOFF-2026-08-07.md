### 5.1 O que é preciso determinar

mês** · linhagem `source_id` · relação pai → filho · casos **"DIA MUDOU"** ·

### 5.2 Schema confirmado — `fixed_variable_payments`

Vem de duas migrations apenas: `037` (criação) e `052` (4 colunas de anexo).

`id` · `company_id` · `kind` (`fixo`|`variavel`) · **`description`** (não existe
coluna `name`) · `amount numeric(10,2)` · **`due_date date`** · `direct_debit` ·
`status` · `recurring` · `period_year` · `period_month` · `paid_at` · `notes` ·
`sort_order` · **`source_id`** (sem FK, sem índice) · `created_by` ·
`created_at` · `updated_at` · `attachment_*`.

**Três factos de schema decisivos:**

1. **`due_date` é `date`, não `timestamptz`** → a hipótese de fuso horário está
   **eliminada** para as datas iguais.
2. **Não existe trigger de `updated_at`.** Só a aplicação o escreve. Um `UPDATE`
   feito à mão no SQL Editor **não** o teria bumped — `updated_at = created_at`
   **não prova** que a linha nunca foi mexida.
3. **Não há constraint única** sobre `(company_id, period_year, period_month,
   source_id)`. A race do `ensureMonth` não tem rede de segurança.

### 5.3 Achados estáticos (só código, sem base)

1. **Variáveis são `recurring = false` por desenho.** `createPayment` grava
   `recurring: input.kind === "fixo"`.
2. **`ensureMonth` clona apenas os fixos.** Comentário literal no código: *"Os
   variáveis nunca se clonam."*
3. **A leitura filtra por `period_year`/`period_month`.**

   → **Consequência:** os variáveis existem **só no mês em que foram criados**.
   Ao abrir qualquer mês seguinte, a lista vem legitimamente vazia. Se o
   proprietário esperava continuidade, o sintoma é exactamente
   "desapareceram" — **provavelmente hipótese D/E, não perda**.

   **Teste barato:** abrir `?mes=2026-06` na UI. Se os variáveis aparecerem lá,
   os dados não foram apagados.

4. **`shiftDate` tem fallback silencioso para o dia 1.**
   `Number(due.slice(8,10)) || 1` — qualquer `due_date` que não seja
   `YYYY-MM-DD` puro faz o dia colapsar em **1**, e todas as linhas afectadas
   ficam com a mesma data.
5. **A clonagem é encadeada:** cada mês clona o mês anterior mais recente. Uma
   corrupção **propaga-se para sempre** para todos os meses futuros e **nunca se
   auto-corrige**.
6. **`ensureMonth` é `SELECT` → `INSERT` sem transação nem constraint única.**
   **Existe race condition real** — dois renders concorrentes do mesmo mês podem
   inserir os fixos duas vezes.
7. **O antigo `CRIAR_PAGAMENTOS.sql` continha `DELETE` + `INSERT` sobre
   Junho/2026** (11 fixos + 28 variáveis, datas hardcoded, uma delas
   `2026-11-09` dentro do mês 6). Foi **removido** na T03 (commit `9863221`).

   ⚠️ **Não assumir que foi executado.** Só o diagnóstico real pode confirmar.
   A assinatura testável: 11 fixos + 28 variáveis, `janela_criacao ≈ 0`,
   `com_origem = 0`, `data_fora_do_mes ≥ 1`, `autores_distintos = 1`.

> **Não é possível concluir só com código** se as datas dos fixos foram
> calculadas mal ao clonar ou sobrescritas na base. Distinguir exige ler
> `due_date`, `source_id`, `created_at` e `updated_at` das linhas reais.

## 15. REGRA DE PRESERVAÇÃO FINANCEIRA — permanente

**ANTES de qualquer alteração financeira, capturar a baseline:**

```
COUNT total
COUNT fixos
COUNT variáveis
COUNT por período
SUM(amount) por período e tipo
MIN/MAX due_date por período
conjunto de ids
conjunto de source_ids
```

**DEPOIS: comparar.**

Nenhuma linha existente pode inesperadamente:

- desaparecer;
- mudar de tipo;
- mudar de valor;
- mudar de data;
- mudar de período;
- mudar de `source_id`.

**Qualquer diferença não prevista → ABORT / ROLLBACK.**

> As queries do diagnóstico (§5) **são** esta baseline. Ao serem corridas, ficamos
> com o "BEFORE" datado para o relatório BEFORE × AFTER do Financeiro V2 —
